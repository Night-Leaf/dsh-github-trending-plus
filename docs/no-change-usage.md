# 不改插件也能用：三条出网路径

插件会自动识别本机的出网方式，不需要改代码，也不需要改插件配置。本文只讲你手动能做的事，以及每条路的边界。

## 先跑一次诊断

```
node scripts/egress-check.mjs --runs=2
```

每行输出 `{run, via, repos, ms, error}`：`repos` 大于 0 就是这一次取数成功，`via` 告诉你实际走了哪条路。`--mode=direct` 只看直连，用来判断本机能否直接访问 GitHub。

## 路一：系统代理（Clash 这类）

**怎么判断**
- 任务管理器里有 Clash、Clash Verge、v2rayN 之类的进程。
- Windows「设置 → 网络和 Internet → 代理」里「使用代理服务器」是开着的，地址形如 `127.0.0.1:7890`。
- 浏览器能打开 github.com；命令行工具不一定能，因为可能只有浏览器走了自己的代理。

**能照做的步骤**
1. 启动代理软件，打开它的「系统代理」开关。
2. 回到 Windows 代理设置页，确认开关已打开、地址端口已填入。
3. 运行 `node scripts/egress-check.mjs --runs=2`，看每行的 `via` 是否为 `system-proxy`。

**前提**
- 代理软件提供 HTTP/HTTPS 代理端口（能处理 `CONNECT`），不只是 TUN 模式。
- 插件和你在同一个 Windows 用户下运行，才读得到当前用户的代理设置。

**做不到的情况**
- 只开 TUN、没开系统代理：插件读不到代理，会落到直连或本机 MITM。
- 代理软件只开 SOCKS5（例如只有 1080 端口）：插件不把 SOCKS 端口当 HTTP 代理，这条路走不通。
- 代理软件的开关被安全软件或公司策略锁住：设置页改不动。
- 插件以服务或别的用户身份运行：读不到你这个用户的注册表代理设置。

## 路二：本机加速器（Steam++ / Watt Toolkit 这类）

**怎么判断**
- 任务管理器里有 Steam++ 或 Watt Toolkit。
- 加速器界面里 GitHub 相关加速项是开着的。
- 浏览器能打开 github.com，但用某些命令行工具访问会报证书错误（`self-signed certificate`、`UNABLE_TO_VERIFY_LEAF_SIGNATURE`）。
- 加速器显示已接管，或 `github.com` 被指到 `127.0.0.1`。

**能照做的步骤**
1. 启动加速器，勾选 GitHub 加速项，保持它运行。
2. 运行 `node scripts/egress-check.mjs --runs=2`。
3. 插件会在首次需要时自动导出加速器的根证书，并缓存到 `%USERPROFILE%\.dsh\github-trending-ca.pem`；若第一次报证书错误，重跑一次通常就能复用。

**前提**
- 加速器把域名指到本机，并在本机 443 上做 TLS 中间人（证书会被替换）。
- 加速器的根证书在「当前用户 → 受信任的根证书颁发机构」或「本地计算机 → 受信任的根证书颁发机构」里。
- 插件有权限读证书库（通常不需要管理员）。

**做不到的情况**
- 加速器只改 DNS/hosts、没有本地 443 监听：连接会直接失败，这条路不成立。
- 加速器只提供 SOCKS/HTTP 代理端口、不做 443 中间人：应该走「路一」。
- 根证书没装进系统证书库，或装在另一个用户的证书库里：插件导出不到匹配的根，仍报证书错误。
- 证书库里有多张同名自签根：插件只信任与实际签发者指纹一致的那一张，其余不认。
- 公司电脑锁了证书库读取：插件拿不到证书，这条也走不通。

## 路三：直连 / DoH

**怎么判断**
- 任务管理器里没有代理或加速器进程。
- Windows 代理设置页是关着的。
- 浏览器能直接打开 github.com；换手机热点也仍然能打开。
- 运行 `node scripts/egress-check.mjs --mode=direct --runs=1` 能返回 `repos >= 1` 且 `via` 为 `direct`。

**能照做的步骤**
1. 关掉 Clash 的系统代理和 Steam++，确保没有本地代理在拦。
2. 运行 `node scripts/egress-check.mjs --mode=direct --runs=1`。
3. 若返回至少 1 条、`via` 是 `direct`，本机直连可用，平时用默认 `auto` 即可。
4. 若直连失败但域名解析有问题，插件会在直连之后自动尝试内置 DoH，不需要你手工填端点。

**前提**
- 本机网络能直接访问 github.com 的 443 端口。
- 系统 DNS 或 DoH 能解析出可用地址。

**做不到的情况**
- 网络对 GitHub 丢包或被防火墙拦截：直连一定失败，脚本退出码非 0，这属于环境不满足。
- 只有浏览器能打开：那多半是浏览器自己的 DoH 或代理在起作用，不代表命令行或插件能直连。
- 公司网络只允许通过代理出网：直连注定失败，改走路一。
- DoH 端点本身也被阻断：直连和 DoH 都不通，改走路一或路二。

## 边界：哪些是插件做的，哪些是你做的

**插件只做只读的事**
- 读当前用户注册表里的代理开关、地址和例外列表。
- 探测常见本地代理端口（7890、7891、7897、7877、10808、10809、1080），只保留能真正建立 `CONNECT` 的。
- 读系统证书库里与实际签发者匹配的那一张根证书，把 PEM 缓存到 `%USERPROFILE%\.dsh\github-trending-ca.pem`。
- 按「系统代理 → 本地代理端口 → 本机 MITM → 直连 → DoH」的顺序逐个尝试。

**插件不写任何系统设置**
- 不写注册表、不开关系统代理、不安装根证书、不改 hosts、不改防火墙。
- 不起本地代理或监听端口，也不修改代理软件自己的配置。
- 诊断脚本同样只读；`--mode=direct` 只是让插件不选代理，不会关掉你正在开的 Clash 或 Steam++。

**你手动做的事**
- 打开或关闭代理软件的系统代理开关。
- 启动加速器、勾选 GitHub 加速项、安装它的根证书。
- 切换网络（例如换热点），判断直连是否可用。

三条路都试过仍然取不到数据，说明当前网络环境不满足；把 `node scripts/egress-check.mjs --runs=2` 的完整输出交给维护者判断。
